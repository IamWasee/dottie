## Overview

Dottie is a macOS menu bar companion app. No Gemini anywhere: Groq talks, Claude Haiku answers requests, GLM and Jev handle the screen, Kokoro speaks and Needle does everyday Mac actions on the Mac. A normal Mac app (Dock icon, Cmd+Tab, Force Quit) whose main window is Home; it also lives in the menu bar and the notch. Clicking the menu bar icon opens a custom floating panel with companion voice controls. Push-to-talk (ctrl+option) turns the user's voice into words with Apple Speech for the talker. A blue cursor overlay can fly to and point at UI elements on any connected monitor.

The only key is a Gemini API key, and it lives on a Cloudflare Worker proxy — nothing sensitive ships in the app. See ROADMAP.md for which features exist so far.

## Architecture

- **App Type**: Regular app (`LSUIElement=false`): Dock icon, app menu, Cmd+Tab and Force Quit. Opening it (Dock, Finder, Spotlight) shows Home; a login-item launch stays in the menu bar. Closing Home doesn't quit, the Dock icon brings it back, and cmd+, opens Home → Settings
- **Framework**: SwiftUI (macOS native) with AppKit bridging for menu bar panel and cursor overlay
- **Pattern**: MVVM with `@StateObject` / `@Published` state management
- **Voice tools**: `DottieVoiceTools` holds voice Dottie's tool declarations and the one dispatch that runs them (`runTool(functionName:arguments:)`); the voice's Claude requests call it. Gemini Live and its WebSocket client are gone. Only about 20 everyday tools are declared (`DottieVoiceToolCatalog.directFunctionNames`); the rest are found with `find_tool` and run with `use_tool` through the same dispatch, so a rarely used tool's how-and-when belongs in its description, not the voice prompt. `point_at_element` only tells the model to use a `[POINT:]` tag.
- **Voice (the only mode; Gemini Live mode was removed)**: no Gemini. Apple Speech → `DottieTalker`: Groq talks (`/chat` with `"provider": "talk"`: the words only, a short prompt, the last 3 exchanges, `GROQ_TALK_MODELS`) and answers small talk itself or replies `REQUEST` (`REQUEST SCREEN` when it's about the screen). Requests go to Claude Haiku (`"provider": "request"`, `REQUEST_PROVIDER_ORDER`, Claude only) with a short tool list (`DottieTalkerProtocol.requestToolNames`, the rest via find_tool/use_tool), a screenshot only when Groq asked for one, and up to 6 tool rounds; tools run through `DottieVoiceTools.runTool`. Claude's tools are marked for prompt caching. Claude gets the direct Mac tools too (`run_applescript`, `open_url`, `browser`, `press_keys`, `type_text`, `apps_and_tools`, `use_app_tool`, `control_device`) and its prompt says Mac tool first, never a screen job, for opening apps, folders and files; the Pre-ship check sends asks through this same request path and fails on a screen job for a Mac action. Kokoro speaks (system voice as backup), with `[POINT:]` tags
- **Background agents ("Dots"; "Clickys" in type names)**: each agent turn runs Google's Gemini CLI headless (`gemini -p … -o stream-json --approval-mode yolo`, `--session-id` then `--resume`) in the agent's folder under `~/Library/Application Support/Dottie/Dots/<slug>/`. `GOOGLE_GEMINI_BASE_URL` points it at the Worker's `/gemini` passthrough and `GEMINI_CLI_HOME` at an app-owned `.cli-home`, so the user's own `~/.gemini` is untouched. Live hands work over with the `start_clicky_task` tool; results show as a notch card.
- **Skills**: a library of Gemini CLI skills (`SKILL.md` folders) in `~/Library/Application Support/Dottie/Skills/`. Each agent's enabled skills are symlinked into its workspace's `.gemini/skills/` before each turn, and the library is passed with `--include-directories` so agents can save new skills there (the app turns a skill an agent saved on for that agent).
- **Routines**: agents set up repeats by ending a reply with `<ROUTINE>{"action":"create","every_minutes":60,"title":…,"task":…}</ROUTINE>` (also update, delete, pause, resume). `ClickyRoutineStore` keeps them in `Dots/routines.json`; a 30-second timer in `ClickyRoster` runs due ones while the Mac is awake and online. Every user turn starts with the agent's current routine list; run turns get a "report what's new" brief. Three failed runs in a row pause a routine. Runs keep their own conversation (fresh every 8 runs, carrying the last report) and run on Gemini, except 24/7 jobs; a reply of exactly `NOTHING NEW` stays quiet and doubles the wait (up to 60 minutes, back to the set pace on a change). An optional `watch_url` is read first and the run skipped while its text is unchanged. A Dot's chat with the user starts a fresh session, with a 6-message handover, after 45 idle minutes or 12 turns.
- **Computer use**: the app target's "Embed cua-driver" build phase runs `scripts/embed-cua-driver.sh`, which puts a pinned, checksum-verified cua-driver release in `Contents/Helpers/cua-driver` (cached in ~/Library/Caches/Dottie-build; offline builds just warn). To update it, bump `CUA_DRIVER_VERSION` in that script. When the driver is found (bundled first, then ~/.local/bin), it's registered in Gemini CLI's settings as two MCP servers, `computer-use` (looking tools only) and `computer-use-act` (looking and input tools), both `cua-driver mcp --direct --embedded` so they inherit the app's permissions; each turn gets only one of them through `--allowed-mcp-server-names`. Each turn sets `CLICKY_CUA_POLICY_FILE` to a look-only or look-and-act policy; act is used only for turns the user allowed or with "Always allow". Agents ask with a `<COMPUTER_USE_REQUEST>` block, which becomes an Allow / Always / Not now card. The same permission covers commands: a turn the user hasn't allowed runs Gemini CLI with `--approval-mode auto_edit` (reading, file edits in its folders, `web_fetch`; `.gemini/policies/dottie-helpers.toml` adds skills and the exact web-search command) and a Claude helper's MausBot bot with approval `auto`; an allowed turn, or "Always allow", gets `yolo` / `full` (`ClickyComputerUse.geminiApprovalMode`, `mausBotApprovalLevel`).
- **Instant lane (no AI)**: spoken and typed turns are checked by `DottieInstantLane` before the talker. Instant commands (`DottieInstantCommands`) are open/quit app, move windows, music, volume, Google/YouTube searches, everyday keyboard shortcuts by name ("minimize" → cmd+M, "new tab", "undo", …) and keys said out loud ("press command shift T"). Learned shortcuts: a Live turn whose tool calls were all replayable (`open_url`, `press_keys`, `run_shortcut`, safe `run_applescript`, `control_device`) is saved under the user's words and replayed without Gemini next time; "when I say X, Y" names one, and "minimize means command M" teaches a key. A turn that only pressed keys is learned even from one word or with "this". Ideas from Atticus (MIT).
- **Needle (on-Mac model, no AI service)**: Cactus Needle 3 and Whistle (Apache-2.0) run inside the app. `scripts/embed-needle.sh` (build phase "Embed Needle") puts a pinned, checksum-verified universal `libneedle3.dylib` in `Contents/Frameworks` and `needle3.cact` / `whistle.cact` in `Contents/Resources/Needle`; `DottieNeedleEngine` opens them with dlopen (nothing happens if they're missing). When the strict lane doesn't match, `DottieNeedleRouter` asks Needle for a tool call from a ≤5-tool set chosen by the ask's words (`DottieNeedleToolset`: apps/windows, music/volume, search, reminders/calendar), acts only when the confidence is high enough and the user's own words back the call up, turns it into instant command words parsed strictly as usual (or Dottie's own `add_reminder` / `add_calendar_event`, times read by `NSDataDetector`), and saves the ask as a learned shortcut. Voice Dottie and screen jobs can hand it one action mid-job with `quick_mac_action` (`DottieQuickMacAction`: strict lane first, then Needle; never replays or naming shortcuts). It also does Mac actions when Gemini can't be reached, nudges `find_tool` by meaning (centered vectors), and, when Speech Recognition isn't allowed, Whistle hears short push-to-talk turns (`DottieWhistleTurnRecorder`). The Needle lab workflow (`scripts/needle-lab`) runs the same Swift code against the real engine on a Mac runner; rerun it after changing the toolsets or bumping the version.
- **Working on its own**: screen-job steps go to the Worker's `/chat` (`"provider": "screen"`, GLM first, one screenshot per step); the model names the app sends (`DottieModelPicker.quickModelName` / `normalModelName` / `carefulModelName`) only label the request, the Worker picks the model. Claude Sonnet through MausBot (`DottieScreenJobClaudeBrain`: the runner's newest turn becomes one message with the screenshot as a file, JSON actions with pixel boxes become function-call parts with the placeholder thought signature; after one miss the Worker's step model does the rest) is off unless turned on in Settings → Working on its own. "Watch me for N seconds", "create a smart replay of me doing this" and "done" are caught on the Mac by `DottieLearningPhrase` in the instant lane and start or stop `watch_and_learn` / `smart_replays` directly. Before any screenshot, `DottieScreenJobGuesser` asks the Worker (`"provider": "plan"`, GLM first, no Claude planner bot) for the steps in words (menus by path, shortcuts, controls by name, links) and does them through Accessibility, finishing without a screenshot when the done text shows on-Mac OCR, else handing over with a note. `DottieWatchAndLearn` ("watch me for 30 seconds") keeps frames plus the smart-replay action lines and has Claude write a how-to (goal, method, where things are), saved in `Watched/howtos.json` and as a library skill for every Dot; screen jobs read matching how-tos. Away mode (`DottieAwayMode`) sends questions, helper computer-use requests and any click on a pay/send/post/delete button (checked on the Mac) to Telegram with Allow / Deny buttons (`DottiePhoneBridge.ask`), never passwords; it retries a failed job once with a different route, texts results and failure screenshots, and logs everything for the "while you were away" report. Helpers get `DottieWorkRoutes.helperInstructions` (connected apps/APIs, then CLI/AppleScript, then the user's browser, then a `<SCREEN_JOB>` block Dottie runs with the result sent back to the helper; Word/Excel files; saving new kinds of tasks as skills) and, unless turned off, the user's Documents, Desktop and Downloads. Shared Claude bots go through `DottieClaudeBot`.
- **Connectors**: Home → Tools also lists sign-in connectors like Claude's (hosted MCP servers through `npx mcp-remote`, OAuth in the browser, 300 s handshake), Roblox Studio's built-in MCP server, and "Bring in my Claude connectors" (Claude Desktop's config and `~/.claude.json`).
- **Code editor**: Home → Code (`HomeCodeView`, `DottieCodeWorkspace`) is a small editor over Projects, the Dots' folders and opened folders: NSTextView with regex colors, cmd+S, a command box run in the file's folder, "Ask Coder" (a helper), and reload when a helper changes the open file. Voice tool `code_editor`.
- **Notes board**: `write_notes` (`DottieNotesBoard`) opens a dark, non-activating notebook panel that scrolls both ways: headings, subheadings, paragraphs, bullet/numbered lists, one-line equations that never wrap, dividers and pictures (a screenshot, one part of the screen found like a drawing anchor, or a web picture/og:image). `place: right` continues the same row, otherwise a new row. Pages autosave as Markdown in `Application Support/Dottie/Notes/`. Text everywhere Dottie writes (board, screen, notes) goes through `DottieMathText.pretty` (math and chemistry symbols) and can carry `DottieInkText` markings: `{red:…}`, `{highlight:…}`, `**bold**`.
- **Live meeting help**: while meeting mode runs, `DottieMeetingLiveHelp` feeds the mic ("You") and the Mac's audio ("Them") separately from `MeetingAudioMixer` into two Apple speech recognitions; a 0.7 s pause ends what someone said. When "Them" ends with a question (or ⌘⇧Return / the notch's "help me"), the last 2 minutes, the user's prep notes and a screenshot only when the screen changed (32×18 fingerprint) go to `/chat` with `"provider": "groq"`, and two or three short lines show in the notch's `.meetingHelp` card, never spoken. Talking points refresh every 30 s; asks are capped at 8 a minute.
- **Groq (mixed with Gemini)**: dictation is Apple's recognizer on the Mac and speech is Kokoro; the Worker has no voice, speech or dictation routes. `/chat` bodies with `"provider": "groq"` (live help, `DottieChat` text-only asks, the guesser's plan, pointing refinement, guides' Gemini fallback and screen-job steps) go to Groq first when `GROQ_API_KEY` is set and the request fits (`GROQ_MAX_REQUEST_TOKENS`, 7000 for the free plan; screen jobs send Groq only their 3 newest screenshots and recent steps via `fittedForProvider`), then Gemini; Dot turns (`/gemini/*` generateContent) that fit go to Groq first too. Groq is asked for boxes in pixels and its answer turned back into `box_2d` (`pixelBoxConversion`). Other small `/chat` requests get Groq as a backup. `worker/src/chatCompletions.ts` converts Gemini bodies to OpenAI chat format for Groq and NIM, and gives their function calls the placeholder thought signature.
- **Paid models (Claude and GLM)**: with `ANTHROPIC_API_KEY` and/or `ZAI_API_KEY` set, `/chat` and Dot turns (`/gemini/*` generateContent) go to them before Groq (`paidProviders` in `worker/src/index.ts`): asks with pictures (screen steps, pointing) to GLM-5.3-Flash on Z.ai first, helpers' turns (`/gemini/*`) only to GLM, other text (quick asks) to Claude Haiku 5.5 first; `PICTURE_PROVIDER_ORDER` / `HELPER_PROVIDER_ORDER` / `TEXT_PROVIDER_ORDER` change the order. Claude is asked through its own Messages API (`worker/src/anthropicMessages.ts`, chat request → Messages and back, pixel boxes like Groq), thinking off. GLM is asked for boxes in its own order, x first on a 0-1000 grid (`box_xy`, `THOUSAND_GRID_LEFT_FIRST`), and the answer turned back into `box_2d`: given Gemini's y-first `box_2d` it often answered x first, which swapped clicks across the screen. Screen jobs send them only their newest screenshots. When every paid one fails, Groq then NIM answer if their keys are set; otherwise the caller gets a 503. Nothing reaches Google.
- **Jev drives screen jobs** (`DottieJevDriver`): after a replay and the guesser, every step Jev gets the goal, the screenshot and one `choice` question listing every move possible now (click any on-screen text read by Vision, type a piece of the user's own words with or without Return, open a site or app the request names, search, scroll, back, done, none fits) plus a `noul` "done?"; it explores by striking off moves that changed nothing on that screen. Unsure, none fits, 3 unchanged moves, 25 steps or a question to answer hands over to the step model with a note of what was done. Risky buttons (buy, delete, send…) are offered only when the request says so. Jev's arms (all options, under its 255 limit, screen texts giving way first): named controls read through Accessibility in one round trip per element (icons with a description, fields, links; 0.25 s cap), an "icon with no words" move that has Jev box it (`DottieJev.findPreciseBox`), double and right clicks on texts the request talks about, a drag between two texts the request names, sideways scrolls, everyday shortcuts with what each does, `quick_mac_action` with the whole request, and "look up app memory" (once per job, only when there is some). Drags, right clicks, quick Mac actions, cmd+Q and cmd+W need Jev's pick to be 50% or more. Typing: jobs whose words involve typing get one background call (`DottieJevTextPieces`, `"provider": "plan"`) that writes the exact text to type (search words, a message, a name; never passwords), merged after the request's own words; text boxes from Accessibility get "click this box and type this" moves (`typeIntoField`, 4 boxes × 3 pieces, with and without Return). Small Jev boxes (screen-job clicks and the icon move) are sharpened on a full-resolution close-up (`DottieJevZoom`); a close-up answer away from the first box is dropped.
- **App memory** (`DottieAppMemory`): for apps with no API or MCP. Every 3 s it checks the front window (Accessibility only); a page it hasn't seen in 3 days, with the window in full view, gets one 1280 px screenshot and on-Mac OCR (no model) stored with where each piece of text sits (0-1000 of the display) in `AppMemory/<bundle>/pages.json`. The user's clicks and every Jev-driven click are noted with the page they opened. Each Jev step first checks for a remembered click the task names (not made only of action words like "Search"), visible now and not yet clicked, and clicks it without asking Jev. Skips password managers and the screen-memory excluded apps, secure input and Dottie itself. Runs only while both `dottieAppMemoryEnabled` (Home → Brain switch) and the Brain's "Remember what's on my screen" (`brainScreenJournalEnabled`) are on. Pages also keep named controls (icons included). The user's clicks, the field they typed into (never the words) and shortcuts are kept as flows per app (`flows.json`, a flow ends after 45 quiet seconds or leaving the app). Jev (its app-memory option) and the step model (`app_memory` tool) read it only when they ask (`DottieAppMemoryRecall`); `read_page_closely` / Jev's ask has Claude (`"provider": "request"`, cost category `app_memory`) read the page's screenshot once and explain every control in Dottie's moves, kept with the page.
- **Jev (find and check)**: `DottieJev` asks the Worker's `/jev` for a box around a named thing or the chance a statement is true. Pointing asks Jev before the box models (not when matching a shared picture); drawings' anchors (`DottieTeaching.locateAnchors`) are GLM's only, never Jev (celly's call), screen-job clicks with a real label use Jev's box over the step model's own, and a finish is held back only when Jev clearly says the done-when isn't on screen. A failure leaves Jev alone for 2 minutes.
- **Model names**: set on the Worker in `wrangler.toml` `[vars]`, not in the app
- **Screen Capture**: ScreenCaptureKit (macOS 14.2+), multi-monitor support
- **Voice Input**: Push-to-talk via `AVAudioEngine` + pluggable transcription-provider layer. System-wide keyboard shortcuts (talk and dictation, both recordable in Settings) via a CGEvent tap.
- **Element Pointing**: In live mode, all displays are drawn side by side into one frame (`captureCompositeFrameForLive`); Gemini's `point_at_element(x, y, label)` is resolved back to a display and converted to AppKit coordinates. In classic mode the model embeds `[POINT:x,y:label:screenN]` tags. Either way the blue cursor animates along a bezier arc to the target.
- **Concurrency**: `@MainActor` isolation, async/await throughout
- **Analytics**: PostHog via `ClickyAnalytics.swift`, off unless `PostHogAPIKey` is set in Info.plist

### API Proxy (Cloudflare Worker)

The app never calls external APIs directly. All requests go through a Cloudflare Worker (`worker/src/index.ts`) that holds the real API keys as secrets.

| Route | Upstream | Purpose |
|-------|----------|---------|
| `POST /chat` | Claude, GLM, Groq, NIM | Chat in Gemini's body and SSE format: `"provider": "talk"` is Groq's talker, `"request"` is Claude, anything else paid providers → Groq → NIM, else 503 |
| `* /gemini/*` | GLM (then Groq, NIM) | Gemini CLI's (Dots') model calls in Gemini's format; the CLI sends the shared secret as its API key. Model listing and countTokens are answered on the Worker; nothing reaches Google |
| `GET /search?q=` | Bing, DuckDuckGo, Wikipedia | Free web search (Google Search grounding is quota-blocked on free keys): asks Bing and DuckDuckGo at once and keeps the results covering the most of the question; `debug=1` shows each engine |
| `POST /jev` | `api.typesafe.ai/v1/systemone` | Jev (TypeSafe's System One model, `worker/src/jev.ts`): the app's System One body (state, screenshot assets, box/yes-no/choice questions) sent with `JEV_API_KEY` and the images header; finds what to click and checks if a job is done |
| `GET /config` | none | Echoes the configured model names |
| `GET /usage` | `InstallUsage` Durable Object | The calling install's own spend for the last 31 days (asks, tokens, estimated dollars, asks with no price, and the same per cost category), added after each `/chat`, `/gemini/*` and `/jev` answer; `?scope=everyone` gives every install's total and is answered only for `UNLIMITED_INSTALL_IDS` |
| `POST /phone/pair`, `/phone/unpair`, `/phone/telegram/<method>` (incl. `/phone/`) | Telegram Bot API, `PhoneRelay` Durable Object | Dottie's own phone bot (`worker/src/phoneRelay.ts`): one-tap pairing link, each Mac's mailbox (long-polled getUpdates) and sends forced to its paired chat. The Mac signs with its install key (`x-dottie-phone-key`) |
| `POST /telegram/webhook` | none | Telegram's webhook for Dottie's bot (secret token derived from the bot token), set by the first `/phone/pair` |
| `GET /health` | none | Says whether the Worker is up and has a model key (`hasModelKey`; the release workflow checks it after deploying) |

**Usage per ask**: every model answer carries `dottieUsage` (provider, model, tokens, seconds, estimated dollars or null) and the Worker logs it as one `[usage]` line (Workers Logs on in `wrangler.toml`). The app (`DottieAskUsage`) logs each as a public `💵 usage ask N` line tied to the user's ask number, counts Jev answers at $0.0001, and shows dollars per provider in Settings → Usage.

**Cost per feature**: every Worker request carries `x-dottie-cost-category`, set by `ClickyWorkerConfiguration.applyAuthenticationHeaders` from the calling file (`DottieCostCategory.filesByCategory`: voice, screen_job_steps, screen_job_plan, jev, guides, pointing, drawing_and_teaching, watch_and_learn, smart_replays, meetings, memory, phone, …; an unlisted file is `other:<file>`). The Worker adds the provider role (`voice/talk`, `voice/request`, `screen_job_steps/screen`, …; `/gemini/*` is `helpers`, `/jev` is `jev`), keeps spend per category in `InstallUsage`, and logs one `[cost]` line per answer. Add a new file that calls the Worker to `filesByCategory`.

**Click checks** (`DottieClickCheck`): each screen-job click logs a public `🎯 click check` line (the model's box center, the point clicked, what moved it: Accessibility snap or Jev, and by how many points) and keeps the screenshot with a red dot at the model's point and a green dot at the click in `Application Support/Dottie/ClickChecks/click-check-NN.jpg`, 30 slots written over in turn.

**Limits per install** (`worker/src/usageLimits.ts`): the app sends its install id (`ClickyWorkerConfiguration.installIdentifier`) as `x-dottie-install`, and after the secret in Gemini CLI's API key (`secret:install-id`). The `InstallUsage` Durable Object (`INSTALL_USAGE` binding) counts each install's requests per area and day, keeps what its answers cost per day for 31 days (`GET /usage`, recorded with `waitUntil` so it never slows an ask) (voice, chat, speech, dictation, helpers, search) and answers 429 once `INSTALL_DAILY_LIMITS` is reached; it also caps how many never-seen installs may start in a day. A caller without an install id is counted by address; `UNLIMITED_INSTALL_IDS` are never limited.

Worker secrets: optional `APP_SHARED_SECRET` (checked against the `x-clicky-secret` header; `/gemini/*` takes it as the API key), optional `GROQ_API_KEY` (quick asks, pointing, screen jobs and Dot turns that fit go to Groq first) and `NVIDIA_API_KEY` (NIM, the last backup); both through `worker/src/chatCompletions.ts`; optional `ANTHROPIC_API_KEY` (Claude Haiku first for text asks and helpers) and `ZAI_API_KEY` (GLM first for asks with pictures), optional `JEV_API_KEY` (`/jev`); optional `TELEGRAM_BOT_TOKEN` (Dottie's own phone bot for one-tap pairing; its mailboxes are the `PHONE_RELAY` Durable Object binding, SQLite-backed so it works on the free plan)
Worker vars: `GROQ_TEXT_MODELS`, `GROQ_VISION_MODELS`, `GROQ_MAX_REQUEST_TOKENS`, `NIM_MODELS`, optional `ANTHROPIC_MODELS`, `ZAI_MODELS`, `PICTURE_PROVIDER_ORDER`, `HELPER_PROVIDER_ORDER`, `TEXT_PROVIDER_ORDER`, `GROQ_TALK_MODELS`, `REQUEST_PROVIDER_ORDER`, `PLAN_PROVIDER_ORDER` (a screen job's plan in words, `"provider": "plan"`; `glm,claude` by default), `JEV_MODEL`, `INSTALL_DAILY_LIMITS`, optional `UNLIMITED_INSTALL_IDS`, `SCREEN_STEP_ATTEMPT_SECONDS` (each model's try on a `"provider": "screen"` step, 8 by default, so the next provider still answers inside the app's 20 s), `SCREEN_STEP_SCREENSHOTS` (how many of a screen step's newest screenshots go to the model, 2 by default; older ones become a note, pictures the user shared are kept), `MODEL_PRICES` (`model=input/output` dollars per million tokens for each answer's estimated cost; Claude Haiku 5.5 built in, others unknown until set)

App Info.plist keys: `ClickyWorkerBaseURL`, `ClickyAppSharedSecret`, `OnboardingVideoURL`, `PostHogAPIKey`, optional `PostHogHost`, `GeminiCLIPath`, `GeminiAgentModel`, `CuaDriverPath`, `DottieUpdateRepository`, `MausBotHelperModel` and `MausBotGameModel`

### Key Architecture Decisions

**Menu Bar Panel Pattern**: The companion panel uses `NSStatusItem` for the menu bar icon and a custom borderless `NSPanel` for the floating control panel. This gives full control over appearance (dark, rounded corners, custom shadow) and avoids the standard macOS menu/popover chrome. The panel is non-activating so it doesn't steal focus. A global event monitor auto-dismisses it on outside clicks.

**Cursor Overlay**: A full-screen transparent `NSPanel` hosts the blue cursor companion. It's non-activating, joins all Spaces, and never steals focus. The cursor position, response text, waveform, and pointing animations all render in this overlay via SwiftUI through `NSHostingView`.

**Global Push-To-Talk Shortcut**: Background push-to-talk uses a `CGEvent` tap instead of an AppKit global monitor so modifier-based shortcuts like `ctrl + option` are detected more reliably while the app is running in the background. The talk and dictation shortcuts are `ClickyHotkey` values (modifiers only, optionally one side's key, or modifiers + a key) saved in UserDefaults and recorded in Settings by `ClickyHotkeyRecorder`. With Accessibility the tap is active so it can swallow a key shortcut's key; without it the tap only listens.

**Voice through the dictation pipeline**: `BuddyDictationManager` owns the mic, permissions, waveform and press/release lifecycle, with Apple Speech turning the turn into words for `DottieTalker`.

**Live session lifecycle**: Sessions with video input are capped at about two minutes, so the socket opens on the first press, closes after 45 idle seconds or on `goAway`, and the last ten exchanges (from Live's input/output transcriptions) are appended to the next session's system instruction. Messages sent before `setupComplete` are queued so the user can talk immediately. A 20s watchdog drops a silent connection.

**Shared URLSession**: Long-lived `URLSession`s are owned by the clients, not per request. Creating and invalidating a URLSession per session corrupts the OS connection pool and causes "Socket is not connected" errors after a few rapid reconnections.

**Native look, light and dark**: Home and the menu bar panel follow the system appearance (native macOS look: system font, sidebar material, accent #0066CC). `DS.Colors` tokens are adaptive `NSColor`s, so surfaces that must stay dark (the notch, cursor overlay, response panel, annotation windows) set `NSAppearance(named: .darkAqua)` on their window. Buttons use `.pointerCursor()` (cursor rects), not `NSCursor` push/pop, which could leave the hand cursor stuck.

**Dynamic Island notch**: The notch panel is one black `DottieIslandShape` that grows out of the hardware notch. Idle it is closed (or shows small wings for unread Dots), listening and thinking open wings beside the notch (eyes + waveform or dots), and everything else (captions, answers, the hover peek, permission and screen-task cards) expands into a card below it with a spring. The window is sized per `IslandPresentation` so it only covers what is drawn.

**Transient Cursor Mode**: When "Show Dottie" is off, pressing the hotkey fades in the cursor overlay for the duration of the interaction (recording → response → TTS → optional pointing), then fades it out automatically after 1 second of inactivity.

## Build & Run

```bash
# Open in Xcode
open leanring-buddy.xcodeproj

# Select the leanring-buddy scheme, set signing team, Cmd+R to build and run

# Known non-blocking warnings: Swift 6 concurrency warnings,
# deprecated onChange warning in OverlayWindow.swift. Do NOT attempt to fix these.
```

**Do NOT run `xcodebuild` from the terminal** — it invalidates TCC (Transparency, Consent, and Control) permissions and the app will need to re-request screen recording, accessibility, etc.

### What CI checks

Every pull request runs the Build workflow on a Mac: it builds the app, runs the unit tests in `leanring-buddyTests/` (the app hosts them but starts nothing, see `isHostingUnitTests` in `leanring_buddyApp.swift`), counts compiler warnings and runs SwiftLint (`.swiftlint.yml`). Warnings and SwiftLint findings may not go over the ceilings in `scripts/ci/budgets.env`; when cleanup lowers a number, lower its ceiling in the same pull request. New pure logic comes with unit tests.

The Release workflow runs in this order so nothing people use changes until everything passed: `prepare` (Worker tests, the Build workflow must be green for the commit, version = one after the newest release, the Worker's address), `preship-check` (the Pre-ship check workflow: everyday asks per feature go to the real model through `/chat` with the real voice prompt and Live's tools, and every tool call is checked the way the app would take it by `DottieToolCallCheck`; a refused call stops the release; add an ask to `PreShipLiveCheckTests.everydayAsks` for each new feature), `build-dmg`, `deploy-worker` (deploys, tries `/health` and `/config`, goes back to the Worker before if they fail), `publish`. Actions are pinned to commits; Dependabot (`.github/dependabot.yml`) moves the pins and the Worker's packages.

## Code Style & Conventions

### Variable and Method Naming

IMPORTANT: Follow these naming rules strictly. Clarity is the top priority.

- Be as clear and specific with variable and method names as possible
- **Optimize for clarity over concision.** A developer with zero context on the codebase should immediately understand what a variable or method does just from reading its name
- Use longer names when it improves clarity. Do NOT use single-character variable names
- Example: use `originalQuestionLastAnsweredDate` instead of `originalAnswered`
- When passing props or arguments to functions, keep the same names as the original variable. Do not shorten or abbreviate parameter names. If you have `currentCardData`, pass it as `currentCardData`, not `card` or `cardData`

### Code Clarity

- **Clear is better than clever.** Do not write functionality in fewer lines if it makes the code harder to understand
- Write more lines of code if additional lines improve readability and comprehension
- Make things so clear that someone with zero context would completely understand the variable names, method names, what things do, and why they exist
- When a variable or method name alone cannot fully explain something, add a comment explaining what is happening and why

### Swift/SwiftUI Conventions

- Use SwiftUI for all UI unless a feature is only supported in AppKit (e.g., `NSPanel` for floating windows)
- All UI state updates must be on `@MainActor`
- Use async/await for all asynchronous operations
- Comments should explain "why" not just "what", especially for non-obvious AppKit bridging
- Log with `DottieLog.notice` / `.warning` / `.error` (`DottieLog.swift`), never `print`: print lines don't reach the Mac's log. Write them like a string; the values put into a line are hidden in the log unless details are switched on, so the fixed words must say what happened
- AppKit `NSPanel`/`NSWindow` bridged into SwiftUI via `NSHostingView`
- All buttons must show a pointer cursor on hover
- For any interactive element, explicitly think through its hover behavior (cursor, visual feedback, and whether hover should communicate clickability)

### Do NOT

- Do not add features, refactor code, or make "improvements" beyond what was asked
- Do not add docstrings, comments, or type annotations to code you did not change
- Do not try to fix the known non-blocking warnings (Swift 6 concurrency, deprecated onChange)
- Do not rename the project directory or scheme (the "leanring" typo is intentional/legacy)
- Do not run `xcodebuild` from the terminal — it invalidates TCC permissions
